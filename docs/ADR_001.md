# ADR 001 — Architecture du pipeline de données SmartBreak

- **Statut :** Accepté
- **Date :** 07/11/2026
- **Contexte :** SmartBreak doit collecter et exploiter des prévisions météorologiques horaires pour Paris. Les données doivent être traçables, contrôlées, transformées et stockées dans une base permettant leur consultation et leur exploitation géographique future.

- **Exigences :**
  - Conserver les réponses originales de la source.
  - Contrôler automatiquement la qualité des données.
  - Isoler les observations non conformes.
  - Garantir la reproductibilité et le rejeu des traitements.
  - Stocker les données structurées dans une base relationnelle.
  - Préparer l'intégration future de données géographiques.
  - Faciliter la maintenance et les tests.

- **Options comparées :**

  | Critère | Option A | Option B |
  |---|---|---|
  | Stockage des données structurées | PostgreSQL/PostGIS | MongoDB |
  | Archivage des réponses originales | Fichiers JSON | Stockage direct en base |
  | Traitement | Pipeline Python modulaire | Script monolithique |
  | Publication | UPSERT SQL | Insertion simple |

- **Décision :**
  - Utiliser Python pour orchestrer un pipeline modulaire.
  - Conserver les réponses originales au format JSON dans RAW.
  - Utiliser PostgreSQL comme base relationnelle.
  - Activer PostGIS pour stocker les coordonnées géographiques.
  - Utiliser des opérations UPSERT pour rendre la publication rejouable sans créer de doublons pour un même instant de collecte.
  - Exposer les données via des vues SQL.

- **Arguments :**
  - PostgreSQL garantit la cohérence relationnelle et permet les contraintes d'intégrité ainsi que les requêtes SQL.
  - PostGIS prépare l'intégration de plusieurs espaces verts et autres lieux géographiques.
  - JSON permet de conserver la réponse originale de l'API sans perdre sa structure.
  - Python facilite la collecte HTTP, la validation, la transformation et les tests automatisés.
  - La séparation des étapes rend le pipeline plus facile à maintenir et à faire évoluer.
  - L'UPSERT permet de rejouer la publication d'une même collecte de manière idempotente.

- **Conséquences positives :**
  - Séparation claire entre données brutes, rejetées et transformées.
  - Traçabilité des traitements.
  - Contrôles de qualité automatisés.
  - Publication reproductible.
  - Architecture extensible à de nouvelles sources.
  - Préparation aux futures requêtes géographiques.

- **Conséquences négatives :**
  - Nécessité de maintenir PostgreSQL et l'extension PostGIS.
  - Gestion de plusieurs formats et étapes de traitement.
  - Les données RAW et CURATED nécessitent une politique de conservation.
  - L'architecture actuelle ne fournit pas encore une interface utilisateur ni un moteur de recommandation complet.

- **Condition de réexamen :**
  - Augmentation importante du volume des données.
  - Intégration de plusieurs sources météo ou géographiques.
  - Besoin de traitements distribués ou de planification avancée.
  - Mise en place d'une application de recommandation en production.

## Portée de la décision

Cette décision décrit l'architecture réellement implémentée dans la première version du projet. Les extensions relatives aux espaces verts et à la recommandation restent des évolutions futures.
